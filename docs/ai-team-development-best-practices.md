# AI-Supported Team Development Best Practices

## Purpose

This document describes a practical way for a software team to work effectively in an AI-fully-supported development environment. The goal is to improve delivery speed without losing engineering quality, maintainability, or team understanding.

## Core Principle

Use AI as a high-speed implementation partner, not as an ungoverned decision maker.

The team should optimize for:

- fast iteration
- clear human ownership
- strong verification
- reusable team knowledge

## Recommended Team Model

### 1. Define responsibility boundaries

AI is effective when its role is explicit.

**AI-led work**

- scaffolding and boilerplate
- test generation
- refactoring support
- documentation drafts
- repetitive API and CRUD work
- investigation summaries
- migration and script generation

**Human-led work**

- architecture decisions
- security-sensitive design
- production risk evaluation
- unclear or conflicting requirements
- final approval for merge

### 2. Break work into small units

AI performs best with narrow, verifiable tasks.

Each task should include:

- a clear goal
- constraints
- acceptance criteria
- expected output files or modules

Good task example:

> Add a user profile API endpoint. Reuse existing auth middleware. Add unit tests and update API documentation. Do not change the database schema.

### 3. Standardize prompts across the team

Prompt quality should not depend on individual skill only.

Maintain shared prompt templates for:

- new feature implementation
- bug fixing
- refactoring
- test generation
- code review
- root cause analysis
- documentation updates

This reduces variation and makes results more predictable.

### 4. Require human checkpoints

A reliable AI-supported process includes human review at defined points.

**Before implementation**

- confirm scope
- confirm expected behavior
- confirm risk level

**Before merge**

- review code changes
- verify tests and checks
- confirm security and maintainability
- confirm that the change matches the requirement

## Recommended Development Workflow

### Step 1: Write a short spec

Before using AI, write a lightweight spec containing:

- problem statement
- target behavior
- constraints
- non-goals
- acceptance criteria

### Step 2: Ask AI for a first draft

Request:

- implementation
- tests
- documentation updates
- assumptions made
- known risks

### Step 3: Review the output critically

Do not review only for style. Review for:

- correctness
- missing edge cases
- security issues
- hidden coupling
- unnecessary complexity
- mismatch with existing patterns

### Step 4: Run validation

Verification must be stronger than generation.

Minimum recommended validation:

- lint
- type check
- unit tests
- integration tests where applicable
- local run or reproducible execution
- security scanning if available

### Step 5: Capture reusable learning

After the task, save:

- the prompt that worked well
- the prompt that failed
- review issues found
- common domain mistakes
- reusable implementation patterns

This turns one-off AI usage into team capability.

## Quality and Safety Rules

### 1. Never merge unreviewed AI output in critical paths

Critical areas include:

- authentication and authorization
- billing and payments
- data deletion
- infrastructure automation
- security controls

### 2. Prefer explicit constraints

Weak prompt:

> Build the feature.

Strong prompt:

> Build the feature using the existing service layer pattern. Do not introduce new dependencies. Add unit tests for success and validation failure cases. Keep API responses backward compatible.

### 3. Keep AI outputs reviewable

Prefer:

- small pull requests
- isolated concerns
- one logical change set

Avoid:

- huge AI-generated diffs
- mixed refactor and feature work
- broad changes without tests

### 4. Make uncertainty visible

AI often sounds confident even when it is wrong.

Require AI-generated work to include:

- assumptions
- open questions
- areas not fully verified

## Team Knowledge Practices

To make AI-supported development efficient at team scale, maintain a shared knowledge base with:

- architecture rules
- coding conventions
- approved prompt templates
- examples of good requests
- examples of bad outputs
- review checklists
- domain-specific rules AI often misses

This can live in an internal handbook, repository docs, or engineering wiki.

## Metrics to Track

Measure team outcomes, not AI activity volume.

Recommended metrics:

- lead time
- cycle time
- review time
- defect rate
- rollback rate
- escaped production bugs
- test coverage change
- time from requirement to validated pull request

Avoid vanity metrics such as:

- lines of code generated by AI
- number of prompts used
- percentage of AI-written code

## Suggested Experiment Projects

To verify an efficient AI-supported process, create several sample projects with different characteristics.

### Project 1: CRUD business application

**Purpose**

Measure AI performance on common application development.

**What to verify**

- speed from spec to implementation
- code consistency
- test completeness
- review effort

### Project 2: Legacy refactor sample

**Purpose**

Measure whether AI can safely improve an existing codebase.

**What to verify**

- regression risk
- refactor correctness
- ability to preserve behavior
- quality of generated tests

### Project 3: API service with auth and background jobs

**Purpose**

Measure performance on more realistic backend complexity.

**What to verify**

- architecture quality
- security gaps
- prompt quality needed for reliable output
- operational completeness

## Standard Experiment Method

Use the same process for each sample project.

1. A human writes a short spec.
2. AI produces the first implementation draft.
3. A human reviews the result and improves the prompt.
4. AI updates code, tests, and documentation.
5. The team records time, issues found, and review effort.
6. The final result is compared with a similar non-AI workflow if possible.

## Recommended Experiment: One Demo Project, Multiple Branches

For your goal, a strong design is to use one demo project and compare multiple branches that deliver the same final scope with different pull request granularities.

This is better than comparing different projects because:

- the product scope stays constant
- the stack stays constant
- the acceptance criteria stay constant
- differences are more likely to come from workflow quality, not project variation

### Demo project shape

Choose one realistic but still manageable demo application, such as:

- a small task management web app
- a simple e-commerce admin app
- a team note-sharing app

The project should be large enough to require:

- UI work
- API work
- data model changes
- authentication or authorization
- tests
- documentation updates

### Branch design

Use three experiment branches that all aim for the same final product state.

**Branch A: small PR granularity**

- many small pull requests
- each PR has one narrow concern
- examples: schema setup, auth middleware, task list UI, test file update

**Branch B: medium PR granularity**

- a moderate number of pull requests
- each PR groups a few related changes
- examples: full auth slice, full task CRUD slice, reporting slice

**Branch C: large PR granularity**

- a small number of large pull requests
- each PR combines multiple layers of work
- examples: backend plus frontend plus tests for a broad feature area

### Rules for fair comparison

To make the comparison trustworthy, keep these constant across all branches:

- same initial repository state
- same written spec
- same acceptance criteria
- same AI toolset
- same model when possible
- same review checklist
- same definition of done

Try to keep the same engineer or engineer pair responsible for each branch workflow so reviewer skill differences do not dominate the results.

### What to compare

Measure both delivery efficiency and engineering quality.

**Efficiency**

- time to first working pull request
- time to final accepted branch
- review turnaround time
- number of review cycles per PR

**Quality**

- defects found in review
- defects found after merge
- test coverage change
- number of regressions
- rework required after review

**Change quality**

- PR readability
- reviewability of diffs
- clarity of commit history
- isolation of failures
- ease of rollback

### Suggested final scope for the demo project

Use one feature set large enough to support different slicing strategies. For example:

1. User authentication
2. Project and task CRUD
3. Search and filtering
4. Audit log or activity history
5. Automated tests
6. Basic deployment or run instructions

All three branches should end with this same scope.

### Recommended execution flow

1. Create the demo project baseline on a common base branch.
2. Freeze the experiment spec before implementation starts.
3. Create `exp/small-pr`, `exp/medium-pr`, and `exp/large-pr` branches from the same baseline.
4. Implement the same target scope on each branch using the assigned PR granularity rule.
5. Review each PR using the same checklist.
6. Record metrics after every PR, not only at the end.
7. Compare the branches after all three reach the same final acceptance criteria.

### Expected learning

This experiment should help you verify:

- whether smaller PRs improve review quality
- whether medium PRs produce the best balance of speed and quality
- whether large PRs increase hidden defects or review fatigue
- how AI output quality changes when work is sliced differently
- which PR size gives the most stable team process

### Likely hypothesis

In many teams, the best result is not the smallest possible PR and not the largest possible PR. A medium PR size often gives the best tradeoff between AI productivity, human review efficiency, and defect control.

That is exactly what this experiment can validate for your team with evidence.

## Practical Operating Rules

Recommended team rules:

- AI may draft code, but validated code only becomes team knowledge.
- Humans own architectural and production-risk decisions.
- Every AI-generated change must be reproducible and testable.
- Prompts, failures, and review findings should be shared across the team.
- The process should reward correctness and learning, not raw generation speed.

## Conclusion

The best AI-supported development teams do not simply use AI more. They use it with clearer boundaries, stronger validation, and better knowledge sharing. A successful team process treats AI as an accelerator inside a disciplined engineering system.

## Official References to Read

Yes, you should read official references for this topic. They help the team build a process based on vendor guidance and recognized risk-management practices, not only personal opinion.

### GitHub Copilot guidance

- **GitHub Copilot documentation hub**  
  https://docs.github.com/en/copilot  
  Use this as the main entry point for product capabilities, team usage patterns, and administration topics.

- **Prompt engineering for GitHub Copilot**  
  https://docs.github.com/en/copilot/using-github-copilot/prompt-engineering-for-github-copilot  
  Read this for practical prompting patterns such as being specific, giving examples, and breaking large work into smaller tasks.

- **Responsible use of GitHub Copilot features**  
  https://docs.github.com/en/copilot/responsible-use  
  Read this to understand capability limits, safe usage expectations, and where human review is still required.

### NIST governance and risk guidance

- **NIST AI Risk Management Framework (AI RMF)**  
  https://www.nist.gov/itl/ai-risk-management-framework  
  This is useful for setting team policies around trustworthiness, risk, measurement, and operational governance.

- **NIST AI RMF Playbook**  
  https://airc.nist.gov/AI_RMF_Knowledge_Base/Playbook  
  Use this as a practical companion to the framework when converting high-level governance ideas into working team practices.

- **NIST Generative AI Profile**  
  https://doi.org/10.6028/NIST.AI.600-1  
  This is especially relevant when your team depends heavily on generative AI tools and needs a more targeted view of GenAI-specific risks.
